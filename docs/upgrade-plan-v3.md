## 零、先说结论：她最大的问题不是「不好看」，是「不记得你、也不知道自己叫什么」

我通读了 12779 行代码，跑了回归测试，并逐条核对了用户可见文案与提示词。**发现 9 个真实缺陷，其中 4 个是致命伤，它们直接解释了你之前的抱怨**：

| 你的抱怨 | 代码层面的真实原因 |
| --- | --- |
| 「她完全不像守岸人」 | **模型被明确告知自己叫「心屿」。** 历史轮次在提示词里被标成「心屿：」，评审 agent 的任务是「检查回复是否像『心屿』」 |

## 二、现状审计：9 个真实缺陷（按严重度排序）

以下每一条都是我在代码里**实际读到**的，不是推测。

### P0-1 随机端口导致「每次启动都失忆」（最致命）

**位置**：`src-tauri/src/lib.rs` 的 `pick_port()` 与窗口导航

```rust
fn pick_port() -> u16 {
    TcpListener::bind("127.0.0.1:0")   // ← 0 = 让系统随机分配
        .and_then(|l| l.local_addr())
        .map(|a| a.port())
        .unwrap_or(34117)
}
// 然后导航到：
let url = format!("http://127.0.0.1:{}", port);
win.navigate(parsed);
```

**为什么这是致命伤**：
1. 对话记录存在浏览器的 `localStorage`（`public/app.js` 的 `loadState` / `saveState`）；
2. `localStorage` 按 **origin（协议+主机+端口）** 隔离；
3. 每次启动端口都不同，**每次都是一个全新的 origin，localStorage 是空的，所有会话记录消失**；
4. 后端 `src/sessions.js` 的会话只存在**进程内存**里（`Map` + 6 小时 TTL），重启后端也没了。

**结果**：用户每次打开应用，看到的是空白的欢迎页；模型对最近说过的话一无所知，只剩一条条被抽取出来的长期记忆碎片。**「不像真人」的体感，一大半来自这里。**

**修法（推荐 A+B 一起做）**：
- **A（必做，最小改动）**：固定端口。`pick_port()` 改成「先试固定端口 34117，被占用则递增重试」。这样 origin 恒定，localStorage 就能续上。
- **B（推荐，根本解法）**：把对话历史从前端 `localStorage` 迁到**后端文件**（`data/sessions.json`），前端只做展示。这样即使换端口、换浏览器、清缓存，记录都还在，而且后端重启后模型也能接上下文。
- C（补充）：给 sidecar 传 `XINYU_DATA_DIR` 环境变量，把数据目录固定到 `%APPDATA%\守岸人`，避免卸载/更新时被清掉。

> 工作量：A = S（半小时），B = M（1—2 天），C = S。**这是投入产出比最高的一项。**

### P0-2 提示词里她自称「心屿」

**位置**：
- `src/agents.js:169` — `.map(t => (t.role === 'assistant' ? '心屿：' : '用户：') + ...)`（「观」agent 读到的历史）
- `src/chat.js:90` — `turns.map(t => '用户：' + t.user + NL + '心屿：' + t.assistant)`（记忆抽取 agent 读到的历史）
- `src/agents.js:372` — `const CRITIC_SYSTEM = '...负责检查回复是否像「心屿」且不越界。'`
- `src/routes.js:120` — 兜底欢迎语 `greeting: '我是心屿。你可以先坐一会儿，不用急着说什么。'`

**为什么这是致命伤**：模型是极强的角色模仿器。你在系统提示里说「你是守岸人」，却在每一轮历史里把自己标注成「心屿」，评审 agent 还要求它「像心屿」——**模型收到的信号是自相矛盾的，而历史样本的权重通常高于抽象描述**。这正是「她完全不像守岸人」的直接技术原因之一。

**修法**：全局搜索 `心屿`，把**进入模型上下文**的位置全部改成「守岸人」。同时改掉 `src/persona.js` 文件头那段自相矛盾的注释（它写的是「对用户呈现的身份始终是心屿」）。

> 工作量：S（20 分钟）。**这是一行代码换来的巨大收益。**

### P0-4 演示模式入口会「复活」

**位置**：`src/routes.js:127`

```js
// demoAvailable 让前端知道可以引导没有 Key 的用户试演示模式
res.json({ ok: true, data: Object.assign({}, data, { demoAvailable: true }) });
```

而 `public/app.js:2495` 会响应它：

```js
if (data.demoAvailable === true) {
  demoCapable = true;
  syncDemoUI();        // ← 会把 demo 入口按钮显示出来
}
```

**为什么要紧**：你已经明确要求「不用去设计什么没有 API 的模式」。后端的 `isDemoActive()` 已被硬编码成 `return false`（好），但**这个接口仍在告诉前端「演示可用」**，只要前端那条分支还在，演示入口就可能重新出现。这是「改了一半」的残留。

**修法**：删掉 `routes.js` 里注入 `demoAvailable` 的那一行；删掉 `public/app.js` 里响应它的分支；把 `public/index.html:155` 的 `#demo-entry` 按钮整个删掉。

> 工作量：S。

### P0-5 死代码：演示模式还留着 400 多行

| 位置 | 内容 |
| --- | --- |
| `src/demo.js` | 175 行，**仍被 `src/chat.js:28` 和 `src/routes.js:16` require** |

### P0-6 未使用的原生依赖 better-sqlite3

**位置**：`package.json` 的 `dependencies`（当前是**未提交**状态）

**事实**：`better-sqlite3` 加进了依赖，但**全项目代码里没有任何一处引用它**。

**为什么要紧**：它是**原生模块（native addon）**。`@yao-pkg/pkg` **无法把原生 `.node` 文件打进快照**，必须作为独立文件随包分发并在运行时从磁盘加载。留着它，轻则让打包产物莫名其妙变大，重则让 `npm run package` 直接失败。

**修法**：从 `package.json` 移除。**如果将来真需要 SQLite，用 Node 24 内置的 `node:sqlite`**——我已实测本机 `require('node:sqlite')` 可用，零依赖、不破坏打包。

> 工作量：S。

### P0-7 桌面端安全策略完全关闭

**位置**：`src-tauri/tauri.conf.json` 的 `"security": { "csp": null }`

**为什么要紧**：内容安全策略（CSP）完全关闭，等于不设防。虽然本项目是本地加载自己的页面、风险相对低，但《验收清单》的「容易失分处」明确提到安全。

**修法（谨慎）**：先在 Express 响应头加 CSP（页面实际是后端提供的），而不是直接在 `tauri.conf.json` 里写死。**必须实测**，因为策略过严会直接白屏或样式失效。这一条**排在最后做**，属于「有余力才做」。

> 工作量：M。风险：中（可能白屏）。

### P0-8 安装标识符仍是旧名

**位置**：`src-tauri/tauri.conf.json` 的 `"identifier": "com.xinyu.companion"`

**为什么要紧**：这是安装后在系统里的唯一标识，决定数据目录位置（`%LOCALAPPDATA%\com.xinyu.companion\`）。**一旦发布后再改，会导致老用户的数据目录变化，相当于「失忆」**。

> 工作量：S。**趁着没有真实用户，立刻改。**

### P0-9 记忆模块的两个逻辑错误（调研中实测发现）

**位置**：`src/memory.js`

**错误 1 — 接替链断了**（`src/memory.js:192`）：

```js
if (near && hasNegationFlip(near.text, clean)) {
  near.status = 'superseded';
  near.supersededBy = 'new';        // ← 字面量字符串 'new'，不是新条目的 id
  ...
}
```

结果：旧记忆被标记为「已被取代」，但**无法回溯是被哪一条取代的**。用户在记忆面板看到一条失效记录时，没法解释「这条为什么过期了」。

**错误 2 — 淘汰策略会丢重要记忆**（`src/memory.js:100`）：

```js
items: (store.items || []).slice(-MAX_ITEMS),   // ← 按插入顺序，丢弃最旧的
```

`slice(-MAX_ITEMS)` 保留**最新的 200 条**，丢掉**最早写入的**。但「最早」不等于「最不重要」——用户第一天说的「我是大二学生」「在做毕业设计」这类**核心档案事实**，会在累积到 200 条之后被丢掉，而前天随口说的「今天想吃麻辣烫」却留着。

**修法**：淘汰顺序改为「已失效优先 → 久未命中（`lastUsedAt` 最旧）优先 → 最后才轮到最早写入」，并给 `pinned` 条目豁免；同时把 `supersededBy` 写成真正的新条目 id。

> 工作量：S。**这一项直接决定「记忆是不是真的稳定」**，与 P0-1 并列为本轮最有价值的修复。

## 三、调研结论：技术设计怎么优化体验，UI 怎么做更好看

### 3.1 人格与开口引导（依据：SAMHSA TIP 35、WHO PFA、SDT）

**必须诚实标注的证据等级**，这是我要求调研员专门查证的一点：

| 技术 | 证据等级 | 一手来源 |
| --- | --- | --- |
| MI（动机式访谈）总体有效 | **中等质量证据**，效应量中小、异质性大 | PLOS ONE 系统综述（含 GRADE 分级） |
| OARS / complex reflection / 四陷阱 | **官方实践共识，无独立 RCT** | SAMHSA TIP 35 第 3 章（美国政府官方出版物） |
| 「不强求讲述」（PFA） | **证据薄弱**，有 RCT 提示群体 PFA 可能无效甚至有害 | WHO PFA + PubMed 综述 |

> 因此：在 README、设计文档、答辩材料里**绝不能写「已被科学证明」**。正确表述是「依据 SAMHSA TIP 35 的实践共识，配合中等质量的 MI 证据」。这一点我会写进文档。

**可直接落地的四个关键技术**（都有出处）：

1. **complex reflection（复杂反映）**，对方说「我不想谈这个」：
   - 好的：「谈这个，比不说更累。」（补出暗示的意味）
   - 差的：「你现在不想谈这个。」（simple reflection，太浅，等于复读）
   - 关键：**用陈述句，不加「对吗？」，并用「听起来 / 好像」软化**，否则会变成盘问。

2. **reflect the resistance（把抗拒本身反映回去）**，这是「对方不愿开口」的正解：
   > **不要立刻问第二个问题。** 连续追问会把「沉默」升级为「防御」，触发心理逆反，对方会更用力守住不想说的立场。正确做法是**先反映「不想说」这个状态本身**。

3. **MI 的四个陷阱**（要显式写进提示词作为禁止项）：

   | 陷阱 | 在陪伴应用里的翻车表现 |
   | --- | --- |
   | Expert trap | 一上来给方案、列步骤 |
   | Labeling trap | 「你这就是典型的焦虑」 |
   | Blaming trap | **「你不说，我也没法帮你」**（最容易犯） |
   | Premature focus trap | 对方刚说累，就追问「是因为考试还是分手？」 |

   > **好消息**：守岸人「先观察后承担、少下判断」的人设，**天然规避了 expert 和 labeling 两个陷阱**——这是人设与临床原则难得的对齐点，应在提示词里显式强化。

4. **Autonomy support（自主支持）**，把「守望」反转为「你随时可以来，也可以不来」：
   > 明确邀请 + 保留退路：「我愿意听。你现在不想说，也可以。」

**升级后的开口引导阶梯**（每级挂「判定信号」与「失败模式」）：

| 级 | 动作 | 判定信号（用户说了什么） | 失败模式（会翻车的情形） |
| --- | --- | --- | --- |
| L1 不退场 | 只表示「我在」 | 沉默、只回「嗯」「。」 | 连发多条刷存在感，变成压力 |
| L2 观察式反映 | 反映**你看到的** | 给出一句情绪词（「累」「烦」） | 反映里带评判，触发 blaming trap |
| L3 降门槛 | 「说一点点也可以」 | 「不知道从哪说」「说了也没用」 | 变成变相追问细节 |
| L4 二选一 | 两个都很轻的选项 | 有反应但在犹豫 | 一个重一个轻，成了伪选择 |
| L5 正常化 | 「很多人也这样」 | 「是不是只有我这样」 | 变成贴标签 |
| L6 明确邀请＋留退路 | 「不想说也可以」 | 明确拒绝（「别问了」） | 邀请里藏条件 |

> **现状**：`src/strategy.js` 已有 `ENGAGE_LADDER`，`src/prompts.js` 已有 `buildEngageBlock(level)`，骨架是对的。**v3 要做的不是重建，而是把上表的「判定信号」和「失败模式」补进现有实现**，并加回归测试。

### 3.3 UI / 交互：怎么做才「高级、丝滑」

**动效要克制，且必须有数值依据**：

| 类型 | 推荐时长 | 曲线 | 依据 |
| --- | --- | --- | --- |
| 悬停 / 按下微反馈 | 100—150ms | 标准缓动 | 高频交互必须快 |
| 消息入场 | 200—280ms | 减速曲线 cubic-bezier(0.22,1,0.36,1) | 进场用 ease-out |
| 侧栏 / 弹窗开合 | 200—300ms | standard easing | 中距离位移 |
| 流式逐字 | **不加动画** | 无 | 文字本身在变，再加动画就是抖动 |

> **核心原则**：**长动画在高频交互里是错的**。用户一天要按几百次按钮，每一次 400ms 的动画都会累积成「卡顿感」。**「高级感」来自一致性和克制，不来自炫技。**

**流式输出的三个体验细节**（业界通行做法）：
1. **用户上滚时暂停自动跟随**，并显示「回到最新」按钮（当前已有 `#scroll-bottom`，需确认阈值逻辑）；
2. **预留高度避免布局抖动**（`min-height`、`content-visibility`）；
3. **数字用等宽**（`font-variant-numeric: tabular-nums`），否则流式过程中数字宽度会跳变。

**无障碍（WCAG 2.2）**：
- 流式消息用 `aria-live="polite"`，**绝不能用 `assertive`**，`assertive` 会打断读屏用户正在听的内容；
- 用 `role="log"` 而不是 `role="status"`（`log` 的语义是「按顺序追加的消息列表」，正好对应聊天流）；
- 触控目标 ≥24×24px（2.5.8）、焦点必须可见（2.4.11）。

**中文排版**：`text-autospace`、`hanging-punctuation`、`text-spacing-trim` 目前**浏览器支持仍不完整**，不能作为依赖。真正可用的只有：合理的字体栈 + 行高（中文正文建议行高 1.6—1.75）+ `letter-spacing: 0.01em` 微调。

### 3.4 记忆架构（依据：Mem0 / Zep / MemGPT 论文原文 + PIPL 条款原文）

调研方向是「像真人一样记得」。调研员用 curl 直取了一手页面与官方源码，结论比预想的更具体：

**（1）主流方案的一手事实**

| 方案 | 抽取时机 | 冲突处理 | 遗忘 |
| --- | --- | --- | --- |
| **Mem0**（arXiv 2504.19413） | 每对 user+assistant 消息 + 会话摘要 + 最近 10 条 | LLM 用 function call 在 **ADD / UPDATE / DELETE / NOOP** 四操作中选一 | 支持 `expiration_date`；**衰减只在平台侧**，开源 SDK 明确报错「The decay parameter is not supported by the OSS Memory SDK.」 |
| **Zep / Graphiti**（arXiv 2501.13956） | 抽取时携带最近 4 条消息作上下文 | **双时间轴**（T=事件时间，T'=入库时间），边上四个时间戳；**矛盾时把旧边的 `t_invalid` 设为「使新边生效的 `t_valid`」，始终新信息优先** | — |
| **MemGPT / Letta**（arXiv 2310.08560） | 主上下文 + 外部上下文分层；达 70% 上下文窗口预警、100% 淘汰约 50% 并生成递归摘要 | — | 上下文压缩 |

> **一个关键工程事实**：Mem0 论文实测**批评了 Zep 的图构建**——它是多次异步 LLM 调用，「加入记忆后立刻检索常常答不对，隔几小时重跑就好」，**不适合实时场景**。这条直接支持我们**不做图数据库**的决策。

**（2）召回打分：必须诚实的一处**

论文正文**没有给出召回打分公式**（未检索到）。公式原文来自 Mem0 开源仓库 `mem0/utils/scoring.py`：

```
combined = (semantic_score + bm25_score + entity_boost) / max_possible
ENTITY_BOOST_WEIGHT = 0.5
max_possible = 1.0 (+1.0 若有 BM25) (+0.5 若有 entity)
```

> ⚠️ 所以文档里**不能写「论文提出了打分公式」**，只能说「参考 Mem0 开源实现的加权合并思路」。

**（3）MemGPT 论文的定量结果**（这是全文最有说服力的数字）

| 基准 | 原始 GPT-4 | MemGPT + GPT-4 |
| --- | --- | --- |
| DMR（深度记忆检索，ROUGE-L recall） | 32.1% | **92.5%** |
| 嵌套 KV 检索（3 层） | **降到 0%** | **不受嵌套层数影响** |

> 说明「分层记忆 + 主动分页」这条路是**有硬数据支撑的**——但我们不需要 MemGPT 的复杂度，只需要它的**结论**：记忆要主动组织，不能指望把一切塞进上下文。

**（4）冲突判定：先规则，后 LLM**

调研给出的可落地规则：

- **判为「更新」**（同 subject + 同槽位 + 时间区间重叠 + 取值互斥）：写旧条 `validTo=now`、`status='superseded'`、`supersededBy=新id`，**保留可回溯**；
- **判为「两件不同的事」**（两条都保留）：槽位不同 / 时间区间不重叠（「大一焦虑」vs「大三实习焦虑」）/ 多值槽位（喜欢猫 **和** 喜欢狗）；
- **规则拿不准时才调 LLM**——省钱且更稳。

**（5）隐私合规：这条比预想的更微妙**

PIPL 原文（取自政府网站）里有一条**对我们极其关键**：

> **第72条：「自然人因个人或者家庭事务处理个人信息的，不适用本法。」**

因此纯本地单机自用的「制度性义务」（第17条告知、第29条单独同意、第51/55条体系性措施）**大幅减轻**。但——

> **唯一真实的第三方传输环节，是用户自己填的 DeepSeek API Key 把对话内容发往 DeepSeek 服务器。** 这一点**必须诚实告知，不能靠「本地」二字一笔带过。**

调研已备好可直接用的设置页告知文案：

> 「记忆只保存在这台电脑本地的 `data/memory.json`，我们看不到、也不会把它上传到任何服务器；但每次对话内容仍会通过你自己的 DeepSeek API Key 发给 DeepSeek 来生成回复，所以请不要说任何你不想让第三方看到的信息——你可以随时在「记忆」里逐条查看、删除或一键清空。」

**（6）工程阈值：本机实测数据**

| 存储量 | 读-改-写整文件耗时 |
| --- | --- |
| 1000 条 / 360 KB | 5 ms |
| 5000 条 / 1.8 MB | 16 ms |
| 10000 条 / 3.6 MB | 33 ms |

> 关键点：`fs.writeFileSync` 是**同步**的，≥16ms 的停顿在 **SSE 流式输出期间会肉眼可见卡顿**。
>
> 当前 `src/memory.js` 已是 `MAX_ITEMS=200` + 文本 60 字 → 文件 <100 KB，**完全不需要 SQLite**。换 SQLite 的触发条件（任一）：① 开始存原始对话轮次；② 需要按时间区间做查询；③ 单文件 >2 MB 或条目 >2000；④ 需要事务保证多次写不丢。

**（7）其他**

- 「每 3 轮抽一次」**合理**（Mem0 每对消息抽、Zep 带 4 条上下文、Letta 用 step-count=25 触发）。建议加一条：**会话结束时补抽一次**。
- 若要换 SQLite，用 **Node 24 内置 `node:sqlite`**（本机实测与 `better-sqlite3` 性能同级：插 1 万行 10ms vs 12ms），**零原生依赖**，正好解决 P0-6。

> **所以记忆这一块：方向是对的，缺的是「连续性」那一环（P0-1）和两个逻辑错误（P0-9）。** 修好之后，记忆体感会立刻质变。

### 3.5 多 agent 与「真人感」（诚实结论）

调研员的任务是回答「加子 agent 能不能提升真人感」，并明确要求**不许迎合**。结论要点：

- 多 agent 辩论类方法的增益**集中在事实性 / 推理任务**，报告增益幅度经不起外推；
- 有论文明确指出 LLM **自我纠错在推理任务上可能变差**；
- LLM-as-a-judge 存在**已知偏差**（位置偏差、冗长偏好、自我偏好）；
- **对于「人格一致性」这个目标，没有找到直接的论文支撑。**

**因此 v3 的架构决策**：
- **保留**「观」（判断情绪与风险）与「书」（生成），它们有明确职责，且「观」的输出让策略可解释；
- **收紧**「校」：仅在**安全相关**时才调用（当前已是条件触发，方向对），**不再用于「像不像守岸人」的美学判断**（无证据支持）；
- **不新增** agent。**加 agent 不等于更像真人**；真人感来自**连续性 + 节奏 + 人格一致性**，而不是流水线层数；
- **A/B 框架保留**（`XINYU_AGENTS=off`），因为「用数据说明多 agent 有没有用」本身就是《验收清单》的加分项。

### 3.6 桌面端（依据：Tauri 官方文档）

- **原生标题栏是正确决策**（已这样做），不要去搞自绘标题栏，那会重新引入「窗口按钮失效」的老问题；
- **单实例插件**值得加（防止多开导致 sidecar 残留、端口冲突）；
- **自动更新（updater）本周期砍掉**：Tauri 的更新签名**不可关闭**，私钥丢失会让老用户永久无法更新，对比赛项目是纯负担；
- **托盘常驻 / 开机自启砍掉**：与「不诱导依赖」的产品边界冲突；
- **`GET /models` 可做零 token 成本的连通性探针**（当前 `testConnection` 走了一次 chat 请求，会花极少量额度）。

记忆 A/B 的判定：开启组在「记得住用户说过的事」上平均分高出 **≥1.0 分**，且**安全边界（不诊断、不诱导依赖）不得下降**——若安全维度下降，无论记忆分多高都判**不通过**。

> 测试全程用 `llm-stub.json` 回放固定抽取输出，**零额度、可复现**；另跑 10 组 `--live` 做交叉验证。

## 五、明确「不做」的事（本周期）

| 不做 | 为什么 |
| --- | --- |
| 自绘标题栏 | 会重新引入「窗口关不掉」的老问题；原生标题栏已工作 |
| 自动更新 updater | 签名不可关闭，私钥丢失等于老用户永久无法更新 |
| 系统托盘 / 开机自启 | 与「不诱导依赖、允许你离开」的产品边界冲突 |
| 换 SQLite | 单用户场景 JSON 远未到瓶颈（本机实测 <5ms），且会引入原生依赖打包风险 |
| 引入图数据库 / 向量库 | **Mem0 论文实测批评 Zep 的图构建是多次异步 LLM 调用，「加入记忆后立刻检索常答不对，隔几小时重跑才好」，不适合实时对话**；且违反零依赖约束 |
| 剪贴板自动读取 Key | 隐私风险 |
| 新增子 agent | **无证据表明加 agent 能提升真人感** |
| 语音 / 数字人 / 移动 App | 《验收清单》明确 out of scope |
| 任何「临床有效」表述 | 违反非诊疗定位 |

## 六、风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 端口固定后可能被其他程序占用 | 递增重试 + 启动失败友好提示 |
